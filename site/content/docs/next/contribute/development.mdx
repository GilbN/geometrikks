You need Python 3.13, [uv](https://docs.astral.sh/uv/), [bun](https://bun.sh/) and Docker for the development database.

## Set up a checkout

```bash
uv sync
bun install
cp .env.example .env
```

`uv sync` creates `.venv` and installs the app along with the `dev` dependency group, which holds pytest and ty. uv includes that group by default. CI runs `uv sync --frozen`, which installs exactly what `uv.lock` pins and never re-resolves it.

Set `APP_ADMIN_PASSWORD` in `.env` before the first run. With no password, no OpenID Connect settings and `APP_AUTH_DISABLED` left off, the app stops at startup with `Auth is enabled but APP_ADMIN_PASSWORD is not set`. The app reads `.env` from the directory you start it in.

## Run the app

Start the dev database, then the app:

```bash
docker compose -f docker-compose.dev.yml up -d timescale_db
uv run litestar --app geometrikks.server.core:create_app run --debug
```

The database settings default to the dev database's user, password, host and name, so `.env` needs no `DB_` lines for it. The app listens on port 8000.

A bare-metal run serves the API but no web UI until there is a frontend to serve. Pick one:

- Set `VITE_DEV_MODE=true` in `.env`. The app starts the Vite dev server itself and serves the UI through port 8000, with hot reload on changes under `resources/`.
- Run `bun run build` once. It writes the production bundle to `public/`, which the app serves as is. Rebuild after each frontend change.

With neither, the UI has no page to load and the startup log warns `no index.html was found`.

### In Docker

`docker-compose.dev.yml` has a `dev` profile that builds `Dockerfile.dev` and runs the whole app in a container as the `app-dev` service:

```bash
docker compose -f docker-compose.dev.yml --profile dev up --build
```

It mounts `geometrikks/`, `resources/`, `tests/` and `data/` for hot reload, sets `VITE_DEV_MODE=true`, tails `nginx_logs/` as its access log and writes the app's own logs to `logs/`. The service loads `.env`, so create it first; compose refuses to start the service without one. It publishes port 8000 too, so stop a bare-metal run before you start it.

### Demo traffic on the map

To see the live route animation without generating log traffic, open the map with `demoTraffic` in the URL:

```text
http://localhost:8000/map?demoTraffic=1       # steady traffic
http://localhost:8000/map?demoTraffic=burst   # overlapping bursts
```

The harness turns Live mode on, sends requests from ten fixed cities around the world and never opens the live-feed WebSocket. It works only when the UI comes from the Vite dev server, so with `VITE_DEV_MODE=true` or the Docker `dev` profile. A `bun run build` bundle ignores the parameter and shows the real live feed.

### Seed data

`tests/seed` fills the database in your `DB_` settings with generated traffic, so the map, analytics and log pages have something to show. Run the app once first so the tables and continuous aggregates exist. It needs the GeoLite2 City database and uses the ASN database when it finds one. A fresh worktree has no `data/geoip/`, so point it at another checkout's files:

```bash
uv run python -m tests.seed \
  --city-db ~/dev/geometrikks/data/geoip/GeoLite2-City.mmdb \
  --asn-db ~/dev/geometrikks/data/geoip/GeoLite2-ASN.mmdb
```

Without `--city-db` it reads `GEOIP_DB_PATH`, and without `--asn-db` it reads `GEOIP_ASN_DB_PATH`. The [seed tool README](https://github.com/GilbN/geometrikks/blob/main/tests/seed/README.md) lists every option.

## Generated API types

The frontend's API client, schemas and route table live in `resources/generated/`. The backend generates them, so after changing a route, a request or response model or an operation, regenerate them and commit the result:

```bash
VITE_DEV_MODE=false uv run litestar --app geometrikks.server.core:create_app assets generate-types
```

CI runs the same command with `VITE_DEV_MODE=false` and fails when `resources/generated/` differs from what you committed. A dev-mode run adds dev-only Vite routes to `routes.json`, and starting the app rewrites these files as well, so run `git status` on `resources/generated/` before you commit and regenerate if something unexpected changed.

## Type checks

```bash
uv run ty check geometrikks tests
bun run typecheck
```

CI runs both, the second against the regenerated types.

## Tests

### Backend

```bash
uv run pytest --ignore=tests/integration   # unit tests only, no database
uv run pytest                              # units, plus integration when the database answers
uv run pytest tests/integration            # the integration suite alone
```

`tests/integration/conftest.py` marks every test in that folder `integration`, and those tests run against a real TimescaleDB. The suite checks whether it can reach the server, and skips those tests when it cannot. So with the dev database running, a plain `uv run pytest` runs the integration suite too.

The integration suite never touches your `geometrikks` dev database. It creates a scratch database, migrates it and sets up the TimescaleDB objects, and drops it when the session ends. It creates the scratch database as a template database, because TimescaleDB never starts its job scheduler in one. No refresh policy then runs while the tests seed and truncate tables. The database user needs the right to create and drop databases.

Override the connection with `IT_DB_HOST`, `IT_DB_PORT`, `IT_DB_USER` and `IT_DB_PASSWORD` (defaults `localhost`, `5432`, `geouser`, `geopass`). `IT_DB_NAME` names the scratch database and defaults to `geometrikks_it`. Give each worktree its own name, because two runs on one name drop each other's database. The name must be 1 to 48 letters, digits or underscores, starting with a letter or underscore; anything else stops the run before a test starts.

CI runs the integration suite on `timescale/timescaledb-ha:pg18-ts2.30`. TimescaleDB 2.31.0 rejects `TRUNCATE` on continuous aggregates, which the `clean_tables` fixture uses, so tests that request it fail there. The dev compose file uses the unpinned `timescale/timescaledb-ha:pg18` image, which moves to new TimescaleDB releases when you pull it. When those tests fail on your dev database, run the suite against a pinned container instead:

```bash
docker run -d --name geometrikks-it-db -p 5433:5432 \
  -e POSTGRES_USER=geouser -e POSTGRES_PASSWORD=geopass -e POSTGRES_DB=geometrikks \
  timescale/timescaledb-ha:pg18-ts2.30
IT_DB_PORT=5433 uv run pytest tests/integration
```

The test session ignores your `.env`. Two environment variables are test hooks that the app's code checks:

- `DISABLE_WAIT=true` makes the waits for the database, for a log file to appear and for a line in a known format try once and return. The test session sets it, and tests that exercise those waits set it back to `false`.
- `DISABLE_ROTATION_CHECK=true` turns off rotation detection in the file source, which watches for an inode change or the file shrinking by 99% or more. Only the test for that switch sets it.

Never set either on a running app. With the first, the app gives up on a database or log file that is not there yet instead of waiting for it. With the second, it keeps reading a rotated log's old file and never opens the new one.

### Frontend

```bash
bun run test        # vitest unit tests
bun run test:smoke  # Playwright browser tests
```

The Playwright tests drive a running app at `SMOKE_BASE_URL` (default `http://127.0.0.1:8000`) and log in with `SMOKE_ADMIN_USER` and `SMOKE_ADMIN_PASSWORD`, falling back to `APP_ADMIN_USER` and `APP_ADMIN_PASSWORD`. Start the app first and install the browser once with `bunx playwright install chromium`. CI runs them against the production image.
